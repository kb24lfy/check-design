# 报告模板

默认中文。开头一句说明实际查看的设计范围、执行的检查及覆盖限制。有 PRD 时注明其标题与可取得的版本。没有版本信息写「未取得」。

只有设计稿时依次输出「CLEAR 法则」「设计检查清单」；同时提供对应 PRD 时，再追加「PRD 与 UI 一致性」。每部分最多一张表格；各部分均为四列，各部分不混表，也不合并问题计数。以下占位内容仅为结构说明，正式报告必须替换成实际规则、依据和图片。

## CLEAR 法则

```markdown
## CLEAR 法则

| 状态 | 维度 | 分析、依据与建议 | 局部截图 |
| --- | --- | --- | --- |
| 🟢 符合 | C 明确 · Clarify | **分析与依据：**用户目标、产品期望结果与当前界面的支持情况；附真实依据和节点链接，目标推断需明确标注。<br>**建议：**支持目标的具体改进方向，或当前有效之处。 | 对应真实局部截图 |
| 🟢 符合 | E 探索 · Explore | **分析与依据：**当前方案的具体限制及依据。<br>**建议：**替代方案、预期收益与主要取舍；无明显改善空间时如实说明。 | 对应真实局部截图 |
| 🟢 符合 | R 关联 · Relate | **分析与依据：**一致性、可复用性与长期适用性的证据及限制。<br>**建议：**统一、复用或扩展建议，不承诺五年后一定可用。 | 对应真实局部截图 |
| 🔴 不符合 | L 精简 · Lighten | **分析与依据：**具体冗余信息、操作或文案及依据。<br>**建议：**可删减内容或文案改写；保留必要要求。 | 对应真实局部截图 |
| 🔴 不符合 | A 布局 · Arrange | **分析与依据：**对比、对齐、亲密、重复的具体表现及依据。<br>**建议：**对应区域的布局改善建议，或当前有效之处。 | 对应真实局部截图 |
```

- 报告按「🟢 符合 → 🔴 不符合」排序；未判定行（状态为「—」）放最后。同一状态内按 C、L、E、A、R 的顺序排列，同一维度的多条结果相邻展示。
- 按 [CLEAR 法则](clear-review.md) 分析，五个维度均保留，不以通用原则复述替代对本次设计的观察。示例文字必须替换为实际分析，截图使用真实图片语法。
- 第三列合并分析、依据、影响和建议，使用短句及 `<br>` 换行。列名固定为「状态／维度／分析、依据与建议／局部截图」，状态按事实使用「🟢 符合／🔴 不符合」，模板状态仅为格式示例，不预设维度结论。不新增分数。证据不足或来源冲突时状态填「—」，分析列注明「未判定」及缺什么，建议注明适用前提；无法取得对应图片时写明原因，不虚构证据。
- 有对应 PRD 时可以将其作为目标与约束依据；未提供 PRD 不追问，无法从设计确认的业务意图标为待确认。没有发现问题时写当前有效之处，不强行提出改动。
- CLEAR「不符合」自动发布定位评论，在第三列「分析、依据与建议」回填结果。与后两部分重复的问题复用同一条评论和截图，不重复计数或发布；符合、未判定及一般建议不评论。

## 设计检查清单

```markdown
## 设计检查清单

| 状态 | 检查项 | 说明 | 局部截图 |
| --- | --- | --- | --- |
| 🟢 符合 | 视觉规范｜具体要求及适用条件 | 已核验事实及[Frame 名称](实际节点链接) | ![对应区域](实际图片路径或支持展示的地址) |
| 🔴 不符合 | 设计规则｜具体要求 | 观察事实、规则冲突、最小修改建议及[Frame 名称](实际节点链接) | ![问题区域](实际图片路径或支持展示的地址) |
| 🟡 待补充证据 | 具体来源类别｜具体要求 | 缺少的属性、组件状态或界面行为证据及[Frame 名称](实际节点链接) | ![相关界面](实际图片路径或支持展示的地址) |
```

- 按「符合 → 不符合 → 待补充证据」排序，每行一条具体规则。来源前缀为「视觉规范」「设计规则」或「基础检查」，保留数值、适用条件和「优先／可」等限定语，不只写大类，也不把问题描述充当规则。
- 视觉不符合写明实际属性、规范值或角色与最小修改建议；待补证据写清具体缺少什么。不同节点状态不一致时拆行，不将局部符合扩展为整体符合。
- 三类检查共用本部分唯一表格，不再分建视觉表、规则表或基础错误表。用户明确只看问题时可隐藏符合行，并注明此展示方式，不声称未检查。
- 范围已完整检查且没有相关项时，可写 `| — | 无适用检查项 | — | — |`，无需截图。规范来源失败或范围尚未确定时不能用这条占位行，直接标记未完成及原因。
- 表后用简短来源说明记录 GitHub 仓库、标准版本、完整提交 SHA、本轮读取时间，以及标准中保留的原来源修订号；原修订号未取得时写「未取得」。规则引用指向本轮提交的真实文件和锚点，不使用随时变化的 main 链接冒充固定版本。只有规则冲突、暂不判定或覆盖受限时追加简短说明，不混入设计问题行。

## PRD 与 UI 一致性

```markdown
## PRD 与 UI 一致性

| 状态 | 检查项 | 对照说明 | 局部截图 |
| --- | --- | --- | --- |
| 🔴 明确不一致 | 具体字段或行为 | **需求：**短引文、适用条件及[PRD 章节](真实来源链接)。<br>**设计：**已核验现状及[Frame 名称](实际节点链接)。<br>**差异／建议：**具体冲突、影响及对齐方向。 | ![对应区域](实际图片路径或支持展示的地址) |
| 🟠 设计覆盖缺项 | 明确要求的状态或内容 | **需求：**明确要求及来源。<br>**设计：**已完整检查的范围及未体现的内容，附相关节点链接。<br>**建议：**补充的样式、状态或标注。 | ![相关区域，仅用于定位](实际图片路径或支持展示的地址) |
| 🟡 待确认规则 | 含糊要求或版本基准 | **需求：**相关原文及来源。<br>**设计：**实际表达及节点链接。<br>**待确认：**需要明确的决定及依据。 | ![待确认区域](实际图片路径或支持展示的地址) |
```

- 列名固定为「状态／检查项／对照说明／局部截图」。PRD 依据、UI 表现、差异与处理建议全部合并到第三列，不增列、不按类别拆成多张表。
- 第三列按「需求 → 设计 → 差异／建议或待确认」书写，使用短句和 `<br>` 换行。需求来源链接放在需求后，精确设计链接放在设计后；每格避免重复链接。
- 按明确不一致、覆盖缺项、待确认排列，同类内优先关键操作和数据含义问题。有真实证据限制时可使用「🟡 待补充证据」行，第三列最后写「待补充：具体所需资料」；不能将其写成覆盖缺项。
- 每行第四列放对应真实截图；缺项截图仅用于定位，不能假装它证明缺失。跨状态或跨页面判断保留相关双方截图与位置，遵循 [资料与证据规则](source-reading.md)。
- 没有明确不一致时写「在本次已核对范围内，未发现明确不一致」，但仍展示实际存在的缺项、待确认或证据限制。有访问限制时同时说明未完成部分，不能写「全部一致」。没有任何需要报告的差异或待确认项时不生成空表。
- 整个 PRD 无法读取时，只在本标题下写「未完成」与原因；禁止虚构对照结果，亦不把本部分改成设计体验自查。
- 表后简述来源版本或读取时间、未覆盖需求章节以及相关运行行为的无法验证边界。不列无关的通用风险清单。

## 评论结果回填

- 检查完成后按 [Figma 原生评论](figma-comments.md) 发布符合条件的问题；不将评论执行情况混为设计检查状态。
- 成功发布或确认已有同一问题评论后，在该行第三列末尾追加 `评论：[查看评论](实际评论链接)`；尚未取得直链时写已核验的评论编号并保留节点链接，不编造评论 URL。
- 应评论但未发布的问题在回填列追加 `未评论：具体原因`，例如未配置 API 凭据、无评论权限、缺少 Figma 链接或无法准确定位。发布结果不确定时写「发布待核实」，不能计为成功。
- CLEAR 最多一张四列表格，设计检查清单和 PRD 对照仍各最多一张四列表格，不另增评论状态列或单独的评论汇总表；各表最后一列展示原始设计证据截图。待确认、待补证据及符合行正常保留，不因不评论而省略。
- 表后简述本次新增、复用已有、未完成的评论数量；没有待发布问题时说明「无符合评论条件的问题，未发布评论」。API 发布以返回的真实评论 ID、正文及位置核验；记录评论编号及可取得的真实链接。不为核验或生成效果截图而自动启动浏览器，也不生成模拟评论截图；三表原有的真实设计证据截图仍保留。
- 凭据或 API 权限阻塞不阻止交付已完成的汇总表；明确哪些评论尚未完成及继续所需条件。

## 交付前核对

- 只有 PRD 时仅引导补充设计稿，不输出上述分析表或检查表；只有设计稿时不出现 PRD 空板块。
- 三个模块的范围与完成状态如实展示；一部分未完成时，不能以另一部分结果声称综合检查通过。
- 每条确定结论具有适用依据和核验过的真实设计证据；位置可定位，不编造节点 ID、文档锚点、版本或规则数值。
- 三个部分各保持四列；Markdown 单元格中的半角竖线需转义；规则前缀可使用全角「｜」。截图放在最右列。
- 不将建议、待确认或未验证项计入已确认不一致；跨部分重复问题可引用但不简单相加为总数。
- 默认在对话交付汇总表，并按约定在 Figma 发布筛选后的问题评论。用户要求导出时再生成相应文件，不默认创建在线文档或通过其他渠道发送报告。
