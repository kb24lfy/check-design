# PRD 与 UI 一致性

仅在本次输入设计稿与对应 PRD 时执行。只比较需求在设计中的体现，不启用无 PRD 的体验自查，不重新拉取已经核验的设计证据。

## 对照流程

1. **拆解需求。** 对本次相关条目记录来源、适用角色或端、触发条件及预期字段或行为。覆盖适用的入口、字段、数据范围、状态、操作、默认值、例外与权限要求，不为无关维度制造检查项。
2. **建立设计映射。** 匹配页面、组件、状态和旁注，检查空态、无头像、已完成等需求明确要求的变体。找不到时先核查相关子节点、复用页和说明；隐藏旧稿不算已展示，但不能忽略实际供复用的状态定义。
3. **核对语义。** 图标可作为操作入口，不自动等同展示字段；同义文案和纯视觉改版不直接构成冲突。「联系电话」与电话图标的差异，应先澄清展示号码还是联系入口，不能断言无法联系。
4. **核对状态与范围。** 区分默认值与可切换能力、当前账号与门店或部门范围、不同角色与状态。「默认图片模式」不证明不能切换；「只调整样式」之外出现配置规则，先确认旧规则及版本。
5. **逐项复核。** 回到需求原文、实际截图和适用条件，排除过期方案、截图裁切、隐藏状态与示例数据导致的误判。只有明确要求且相关设计范围完整核查后，才能报告设计覆盖缺项。
6. **输出。** 按 [报告模板](report-template.md) 在独立的「PRD 与 UI 一致性」部分呈现，一张四列表格。需求原文与来源、设计事实与节点链接、差异及建议合并在「对照说明」，截图独占第四列。

## 分类门槛

| 状态 | 使用条件 | 表达方式 |
| --- | --- | --- |
| 🔴 明确不一致 | 同一角色、状态、适用条件下，PRD 明确要求与可见设计或明确标注直接冲突 | 写清需求、现状、冲突与影响；建议对齐设计，或确认后修订 PRD |
| 🟠 设计覆盖缺项 | PRD 要求明确，完整检查本次相关页面、变体及说明后，仍未体现对应内容 | 写「本次设计范围未体现」，列已检查范围及缺失内容，不写「产品不支持」 |
| 🟡 待确认规则 | 需求含糊、版本或替代方案不明、旧规则缺失，无法确定应遵循哪项要求 | 写出双方依据与待明确的决定，不计入已确认不一致 |
| 🟡 待补充证据 | 要求明确，但相关页面、状态、原型说明或文档内容因未提供、截断、无权限等原因无法核验 | 写明缺失证据与已查范围，不当作覆盖缺项或已确认问题 |

只有前三类发现时只输出实际存在的类别；「待补充证据」是需要时使用的证据限制状态，不增加表格列数。整个 PRD 无法读取时，直接标记本部分未完成，不制造一整表待补证据条目。

## 重要边界

- 静态设计不能验证真实权限控制、跨页保留筛选、接口统计、响应时间、按钮实际跳转、后台计算或运行时可访问性。这类内容放在本部分末尾的「无法验证／检查边界」，不计入不一致数量。
- 没有原型连线不等于交互不存在；没画结果页不等于运行时没有反馈。仅有潜在风险而无 PRD 明确要求或直接冲突，不升级为缺陷，不自动补充体验建议。
- 日期、金额或时长看似冲突，先排除示例数据、跨日、休息、修正工时及税费等解释。不能从示例推定后台算错；缺少必要口径时待确认。
- 与 PRD 无关、可直接确认的错别字、遮挡和同一界面同对象文字矛盾，由设计检查清单按基础错误规则处理，不在本部分另建「设计自身问题」板块。设计模块暂停时不得偷偷改放本部分并声称规范检查已完成。
- 用户明确指定的本次基准优先用于选择资料；资料内部或 PRD 与规范互相冲突时保留双方证据，受影响项暂不判定，不能自行裁决。
- 同根因合并位置；关键任务结果、数据含义、操作与字段差异优先，轻微术语差异在后，不强行分 P0/P1。
- 已核对且一致的条目可保留在内部映射中，默认不逐项输出符合行。没有明确不一致时如实说明，同时保留实际存在的缺项、待确认或受限情况。
