# CLEAR 法则

用于报告第一部分。五个维度定义和适用要求先读取本轮 GitHub 快照的 `standards/clear.md`；本文件规定状态、排序、证据和评论执行方式。采用用户提供的五个维度，基于本轮真实设计证据分析，不将其作为新增的 Lygo 强制规范。输出格式见 [报告模板](report-template.md)。

| 维度 | 核心问题 | 分析要求 |
| --- | --- | --- |
| C 明确 · Clarify | 用户究竟想得到什么？我们希望用户得到什么？ | 说明用户目标、产品期望结果，以及页面的信息和主要操作是否支持这些目标。有 PRD 时引用明确目标；只有设计时将目标推断标为「基于界面推断」，无法确认的目标写待确认，不编造业务意图。 |
| L 精简 · Lighten | 哪些内容可以删除？文案能否更直白？ | 找出重复信息、非必要步骤、难懂文案，给出具体删减或改写建议；保留任务必需信息、PRD 明确要求和必要提示。未确定内容用途时提出条件性建议，不直接认定应删除。 |
| E 探索 · Explore | 有没有更简单、更新颖、更高级的方案？ | 针对观察到的实际问题提出可执行的替代方案，说明预期收益与主要取舍；将「更高级」落到清晰度、操作效率、表达质量等可解释的改善，不为新颖而强行改变已有效的设计。没有明显改善空间时如实说明。 |
| A 布局 · Arrange | 对比、对齐、亲密、重复，是否都遵守了？ | 分析视觉层级、对齐、相关信息的分组与距离、重复元素的一致性，并定位到具体区域。数值是否符合规范仍由设计检查清单判定；这里说明布局对理解和操作的影响。 |
| R 关联 · Relate | 是否统一、可复用？五年后是否仍可用？ | 分析当前范围内的跨页面一致性、组件复用和扩展适应性。视觉相似不等于已使用同一组件，组件复用需属性证据。「五年后」作为长期适用性的检视问题，讨论内容增长、状态扩展和维护，不承诺未来可用性。 |

## 状态与判定

报告第一列为「状态」，正式状态只有 `🟢 符合`、`🔴 不符合`，其后为「维度／分析、依据与建议／局部截图」，共四列。第三列合并观察事实、依据、影响及修改建议，用短句和 `<br>` 分隔。

- 报告按「🟢 符合 → 🔴 不符合」排序；未判定行（状态为「—」）放最后。同一状态内按 C、L、E、A、R 的顺序排列，同一维度的多条结果相邻展示。
- **符合：**已核验的具体页面或状态支持该维度的要求，说明当前有效之处；只代表所列范围，不宣称整个维度或全部设计通过。
- **不符合：**有明确目标或适用的 CLEAR 要求，真实截图、文本或属性直接证明存在具体障碍、冗余、理解冲突、布局或一致性问题。写清事实、依据、影响及修改建议，定位到真实问题区域。
- 五个维度均需覆盖。同一维度存在独立问题或不同状态时拆行；一个问题涉及多个维度时合并或交叉引用，不能重复计数和发布。
- 证据不足、目标未确认或来源冲突时，状态填 `—`，在分析列写「未判定」及具体缺失依据；这不是第三种正式状态，不能强行判符合或不符合，也不评论。
- 单纯审美偏好、存在另一种可行方案、没有采用新颖方案，均不能直接判不符合。E 探索须证明当前方案有具体限制及可行改善方向；R 关联不以无法保证五年后可用为不符合。优化建议可保留在符合行，但不因此评论。
- 不新增分数或通过率，不将 CLEAR 的判断冒充 Lygo 数值规范或 PRD 明确要求。

CLEAR 与另外两部分复用截图和节点证据；同一问题引用对应检查项，避免重复长篇描述和重复计数。规范或 PRD 暂不可读时，CLEAR 可继续分析有证据的设计范围，同时说明限制；不能用 CLEAR 代替尚未完成的正式检查。

## 评论

最终状态为「🔴 不符合」的 CLEAR 问题按 [Figma 原生评论](figma-comments.md) 自动发布到对应位置，使用 `section: "CLEAR 法则"`、`status: "不符合"`。标题为 `【CLEAR｜不符合：维度 · 具体问题】`，正文以 `【当前】：`、`【依据】：`、`【影响】：`、`【建议】：` 分行说明；依据可引用本文件的具体维度、已核验 PRD 或设计事实，不虚构外部标准。保留字段括号、不展示裸节点 ID。

跨 CLEAR、设计检查清单、PRD 对照为同一问题时仅发布或复用一条评论，正文列明不同依据，在各表对应行回填同一个评论编号。符合、未判定及一般优化建议不评论。
